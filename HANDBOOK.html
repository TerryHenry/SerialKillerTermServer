Overview

Serial Killer Terminal Server turns a Raspberry Pi into a console server — the kind of appliance you'd otherwise buy as a Digi PortServer or Opengear box. Plug in one or more USB-serial adapters, wire them to routers, switches, lab equipment, or anything else with a serial console port, and it lets your team reach any of them over SSH instead of walking over with a laptop and a cable.

Two interfaces make up the appliance: a web admin UI for configuration, and an SSH server that end users actually connect through to reach a serial port. They're independent — you don't need a web-UI account to use SSH, and SSH users never see the admin UI.

No hard limits

Configure as many serial ports and SSH users as you want — nothing in the software caps either. The real ceiling is physical: how many USB-serial adapters you can plug in (via a hub if needed) and the Pi's own RAM/CPU. The one genuine limit is the web admin account — there's only one, not a list.

First login

  1. Visit https://<pi-hostname-or-ip>:8443 in a browser. The certificate is self-signed, so you'll get a warning — proceed past it.
  2. Sign in with the default account: admin / letmein0!.
  3. You'll land directly on a password-change screen and can't do anything else until you set a new one. This is enforced by the server itself, not just hidden by the page, and it won't accept letmein0! as the replacement.
  4. Once changed, you're in. Head to Serial Ports and Users to start configuring.
Note

Changing this password only rotates the web UI login. See the next section — there are two other credentials on this device that don't change automatically.

Three account systems, not one

It's easy to assume "the password" is one thing on an appliance like this. Here it's three separate systems, each with its own purpose and its own credentials:

SystemUsed forWhere it's managedDefault
Web admin login Configuring the appliance itself Admin Account tab admin / letmein0! — forced change on first login
SSH console users Reaching serial ports day-to-day Users tab None — you create every account
Pi's own Linux login Shell/SSH access to the Pi itself on port 22, for OS-level maintenance passwd, at the Linux shell admin / letmein0! — not force-rotated

The console-server SSH port (2222) and the Pi's own OS-level SSH (22) are easy to conflate because they're both "SSH to the same box" — but port 2222 drops you into a serial port, while port 22 drops you into a Linux shell on the Pi. See Security notes for what to do about the Linux account's default password.

Web Admin UI

Ten tabs across the top of the admin UI. Here's what each one does.

Dashboard

The landing tab — a live overview, updating automatically every few seconds without a page refresh.

  • CPU, Memory, Disk — each shown as a percentage with a bar that shifts from the accent color to amber at 70% and red at 90%, plus the raw used/total underneath for memory and disk.
  • Connected Clients — the current SSH session count across every port.
  • Serial Ports — every configured port, alphabetically, live: a Present/Missing status pill (whether its device file actually exists right now — the first place to look if an adapter drops out or a USB hub loses power) alongside how many clients are connected to it.

Server

Controls the SSH console server — the thing end users actually connect to on port 2222.

  • Listen port — defaults to 2222, chosen to stay clear of the Pi's own SSH on 22.
  • Port picker menu — when on, a user with no port of their own sees a numbered list of ports to choose from after login. When off, such a user is told to contact an administrator instead.
  • Start automatically on boot — on by default.
  • Login banner — free text shown to every SSH user right after connecting.
  • Start/Stop — the pill next to the button shows live status. This is a real disable switch, not just a pause: Stop persists, so SSH-to-serial stays off even across a reboot, until you click Start again.
  • Host key fingerprint — shown here so you can verify it out-of-band before trusting a new SSH connection.

Web Console (HTTPS-to-Serial)

A toggle here turns browser-based serial access on or off for every account on the Users tab at once — off by default on a fresh appliance. When enabled, those same accounts can sign into /terminal with their username and password and get a console right in the browser, alongside SSH. Turning it off immediately cuts off new logins and connections; it doesn't touch SSH access at all. Hover the ⓘ next to the toggle for the exact URL to reach it at.

Backup & Restore

Download Backup saves everything in the app's config — SSH/TFTP/web settings, serial ports, users, and admin accounts, including password hashes and public keys — as a single JSON file.

Include SSH host key (off by default) additionally embeds the Pi's SSH private host key in the backup. With it, restoring reproduces this device exactly, including the same host-key fingerprint, so existing users don't get a "host key changed" warning after a re-flash or SD card recovery. Without it, restoring still works fine, but the Pi gets a fresh host key identity.

Restore from Backup replaces the entire current configuration with the contents of a chosen backup file, after a confirmation prompt — there's no partial or selective restore. The page reloads automatically once it's done; a restored host key takes effect after the service is restarted.

Handle with care

A backup file contains password hashes and SSH public keys for every account on the appliance — and, if you opted in, an SSH private key. Store it somewhere you'd trust with those credentials — and remember restoring rolls back every admin's password too, to whatever it was when that backup was taken.

Network

Everything about how this Pi reaches (and is reached over) the network.

  • Interfaces — every Ethernet/Wi-Fi interface NetworkManager knows about, its connection state, IP address, and the connection profile name it's using.
  • Public IP — this Pi's IP as seen from the internet, when it has outbound access. Blank if it doesn't.
  • Refresh — re-checks everything above on demand rather than waiting for the periodic update.

Wi-Fi

Enable/Disable Wi-Fi toggles the radio itself. Scan for Networks lists nearby SSIDs with signal strength and security type — click Use on one to fill in its SSID, then enter the password and Connect. You can also just type an SSID directly if it's hidden or out of range of the scan.

Time & DNS

  • NTP Server — defaults to pool.ntp.org. The pill next to it shows whether the clock is currently synced.
  • Timezone — type to search the full IANA timezone list (e.g. America/New_York).
  • DNS Servers — shows what's actually in effect right now, whether that's from DHCP or a previous override. Enter one or more servers (comma or space separated) and Save to override, or click Use DHCP to go back to whatever the network hands out automatically.
Under the hood

The app itself runs as an unprivileged system account. Wi-Fi, DNS, NTP, and timezone changes all go through one narrowly-scoped, fixed-purpose helper script that a sudoers.d rule (validated with visudo before it's ever installed) permits that account to run as root — never a broad or wildcard sudo grant.

Serial Ports

Add one entry per physical serial line, sorted alphabetically by label. Refresh next to the device-path field lists what the Pi currently sees plugged in, so you're not guessing at paths — devices already assigned to another configured port are left off that list, so you can't accidentally point two ports at the same device.

  • Label — whatever the device actually is: "Core Switch Console," "Lab Router 3."
  • Device path, baud, data/stop bits, parity, RTS/CTS — standard serial parameters, matched to the equipment on the other end.
  • Access mode — who can connect at once, and who can type. Covered in full in Access modes & permissions.

Ports are referenced by ID internally, so renaming a label later doesn't break any user's assignment to it.

Use stable paths

/dev/ttyUSB0-style names are assigned by detection order at boot or plug-in time — they aren't guaranteed to stay the same across a reboot or a replug, which can silently point a port at the wrong physical device. Refresh lists /dev/serial/by-id/… paths instead whenever they're available (derived from each device's own USB descriptor via udev, already set up on the Pi with no configuration needed) — always prefer those over a raw ttyUSBx path. If you have two identical adapters that don't expose a unique serial number, their by-id names may collide; in that case /dev/serial/by-path/… (stable by physical USB port instead of device identity) is the fallback, as long as you always plug that adapter into the same physical port.

TFTP

An optional TFTP server, off by default — useful alongside serial console access for the classic workflow of pushing firmware or config files to network gear that only accepts them over TFTP.

  • Listen port — defaults to the standard 69; the appliance is specifically granted permission to bind it without running as root.
  • Allow uploads — when on, clients can write files in, not just read them.
  • Root directory — /opt/terminalserver/data/tftp on the Pi. Everything served or received lives there.

TFTP Directory

The same tab lists what's actually in that root directory — name, size, and when it was last modified — so you don't need a separate shell session on the Pi just to check what's there.

  • Upload File — push a file from your own machine straight into the TFTP root (up to 1 GB) without needing a TFTP client at all.
  • Click a filename to download it directly from the browser.
  • Delete asks you to confirm, then removes the file immediately — there's no undo.

Users

Each row is one console account — unrelated to the web admin login. Rows are sorted alphabetically by username.

  • Authentication method — password, an SSH public key, or either. (Public-key auth only applies to SSH; the web console is password-only.)
  • Permission — Read/write or Read-only. Explained together with port access modes below.
  • Default port — assign one and the user is dropped straight into it on login, no menu, ever. Leave it unset and they see the port picker (if it's enabled) instead.

Sessions & Log

Sessions

Everyone currently connected across both access channels — SSH and the web console — in one list: which Method they came in on, which port they're on, and since when. Disconnect ends a session immediately regardless of channel — useful if someone's connection is stuck holding an exclusive port open.

Log

A live stream of connect/disconnect events and server activity, including the TFTP server. It persists — the last 2,000 lines are kept on disk, so reopening the tab or rebooting the Pi doesn't lose history the way an in-memory-only log would.

Admin actions are tagged [AUDIT] right in this same stream — who logged in or out (including failed login attempts), changed a setting, added or deleted a port/user/admin account, restored a backup, and so on — so accountability lives alongside the rest of the activity instead of a separate place you'd have to remember to check.

Admin Account

My Account

Change your own password here at any time — independent of the forced first-login change covered earlier.

Admin Accounts

The web UI supports more than one administrator. Add one per person rather than sharing a single login — combined with the audit trail in the Log tab, that means every change is attributable to whoever actually made it.

  • A new admin you create sets their own password immediately — there's no shared default to force-rotate, unlike the original seeded account.
  • You can't delete the account you're currently logged in as, and the system won't let the last remaining admin account be deleted at all — there's always a way back in.

Connecting over SSH

This is what your team actually uses day-to-day. No web browser involved.

# a user with a port already assigned to them
ssh -p 2222 alice@terminalserver.local

# a user without one sees a numbered picker instead, e.g.:
Available serial ports:
  [1] Core Switch Console  (/dev/ttyUSB0 @ 9600)
  [2] Lab Router 3         (/dev/ttyUSB1 @ 115200)  [2 connected]

Enter port number (or "q" to quit): 1

While connected

Everything you type goes straight to the serial device, and everything it sends back appears in your terminal — a direct pass-through, not a wrapped protocol.

Kbd

Press Ctrl+] at any time to detach from the current port and return to the picker menu (if a picker is available to you) without ending your SSH session.

If your assigned port isn't available

Users with a default port assigned never see the picker menu — that's deliberate, since they're meant to only ever reach one thing. If that port has been deleted, can't be opened, or drops mid-session, you're disconnected with a clear reason instead of being handed a menu you were never meant to see.

Connecting over the Web

The same console users can also get a serial console straight in the browser — no SSH client needed.

Off by default

Turn it on first from the toggle on the Server tab. Until an admin does, /terminal shows a "disabled" message instead of a login form — SSH access is unaffected either way.

Once enabled, visit https://terminalserver.local:8443/terminal (or the Pi's IP) and sign in with a console-user username and password — the same accounts from the Users tab, not an admin account. This is a separate login from the admin UI, even if you're already signed in there.

  • A user with a default port assigned connects straight to it, same as over SSH.
  • A user without one sees a port picker in the browser instead (only if the port picker is enabled on the Server tab) — by label only, not the underlying device path.
  • Read-only users and read-only/shared port access modes are enforced exactly as they are over SSH — see Access modes & permissions.
  • Disconnect ends the session and returns to the login screen.
SSH still works

The web console is an additional way in, not a replacement — the same users can keep connecting over SSH on port 2222 exactly as before.

Access modes & permissions

Two independent settings decide who can type on a given connection: the port's access mode, and the user's permission. Both have to allow writing for a session to actually be able to type — either one set to read-only wins.

Port access modes

ModeConcurrent sessionsWho can type
exclusiveOne at a timeThat one session
shared-rwUnlimitedEveryone attached — input from any of them reaches the port, and everyone sees all output
first-writeUnlimitedOnly the longest-connected session; if they disconnect, the next-oldest remaining session takes over automatically, live
shared-roUnlimitedNobody — pure monitoring

User permission

Independently of the port, each user is read-write or read-only. A read-only user can never type, no matter how permissive the port is — useful for an observer or trainee account that should only ever watch.

Example

A shared-rw port with one read-write user and one read-only user behaves like first-write for that pair — except it's enforced per-account, not by connection order, so it doesn't change if they reconnect in a different sequence.

Transferring files with TFTP

Once started on the TFTP tab, point any standard TFTP client at the Pi's address.

# pull firmware.bin from the Pi's TFTP root
tftp terminalserver.local
tftp> binary
tftp> get firmware.bin

# push a config backup up to the Pi (needs uploads enabled)
tftp> put switch-config.txt

Files land in and are served from /opt/terminalserver/data/tftp on the Pi — drop firmware there ahead of time if devices will be pulling it, or leave uploads on if they'll be pushing configs back.

Security notes

Change the Linux account password too

The web UI forces a password change on first login; the underlying Raspberry Pi OS account (port 22, admin / letmein0!) does not. Run passwd after logging in over SSH on port 22 if you haven't already.

The web UI's certificate is self-signed

Generated locally on first boot, fine for a trusted LAN. If you're exposing the admin UI beyond one, put it behind a reverse proxy or VPN, or swap in your own certificate at /opt/terminalserver/data/tls/ on the Pi.

Give accounts the narrowest access that works

Assign a default port to anyone who only needs one device — it also means a dropped or deleted port disconnects them instead of ever exposing the wider picker menu. Reach for read-only for anyone who should watch but never type.

The web login locks out after repeated failures

Five failed attempts for a given username from a given address lock that pair out for five minutes — even a subsequently-correct password is rejected until the lockout clears. Basic brute-force protection, tracked in memory only, so it resets on a service restart.

Troubleshooting

SymptomWhat it means
Port "X" is already in use. That port is set to exclusive and someone else already holds it. Wait for them, disconnect them from the Sessions tab, or switch the port to a shared mode.
Your assigned serial port no longer exists. An admin deleted the port this user was assigned to. Assign a different one from the Users tab.
"This session is read-only" / keystrokes don't appear Either your account is set to read-only, or the port's access mode doesn't currently grant you write access (e.g. shared-ro, or first-write and someone else got there first).
Browser warns the connection isn't private Expected — the certificate is self-signed. See Security notes.
Locked out of the web admin UI There's no self-service reset. Someone with SSH access to the Pi (port 22) can delete /opt/terminalserver/data/config.json's web section values or restore from a backup to re-trigger setup — back up that file once you've configured things.
Can't log into /terminal with an admin account Expected — the web console only accepts the console users from the Users tab, the same ones SSH uses. It's a separate login from the admin UI on purpose.
Wi-Fi radio won't turn on, or Connect fails Confirm the Pi has Wi-Fi hardware and NetworkManager is managing it (nmcli device status over SSH on port 22). If the sudoers rule failed validation during setup (see /opt/terminalserver/data/setup.log), Wi-Fi control is unavailable until that's fixed.
